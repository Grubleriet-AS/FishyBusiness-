# Steg 138, DRIFT2: varsel når Supabase er nede, og serverens tall (D3–D4)

**Ferdig når:**
1. Et systemd-timerskript på spillets server (`ubuntu-8gb-hel1-1`) spør Supabase hvert minutt (`/rest/v1/` med den publiserbare nøkkelen, bare statuskode og svartid). Etter to bom på rad sendes én push gjennom ntfy.sh, og én til når databasen svarer igjen. Ingen spillerdata eller nøkler går i varselet.
2. Emnet hos ntfy.sh er en tilfeldig streng som står i `/etc/dsb-vakt.env` på serveren (ikke i repoet), og Jonas har fått beskjed om å abonnere på det i ntfy-appen (`docs/spill-dette/138.md`).
3. `tools/server/status.sh` skriver CPU, minne, disk, I/O-ventetid, reléets `/stats`, Caddy-feil og forespørsler per time, og den bare leser. Jonas kjører den med SSH, og tallene limes inn i `docs/systemer/publisering.md`.
4. `setup.sh` installerer timeren og skriptet og tåler å kjøres på nytt. `bash -n` og en lokal kjøring av vakta mot en stedfortreder (200, 503, ikke svar) viser at den varsler én gang og så ved friskmelding.

**Bakgrunn:** `docs/planer/drift-billig-og-stabil.md` (D3, D4, V3 A: Jonas 17.11.2026 «Push via ntfy.sh»). Supabase hang 17.11.2026 fra 11:45 til 12:15 UTC, og varslene inne i databasen (`uptime_tick`, `err_alert`) kunne ikke si fra, fordi pg_cron ikke startet jobbene.

**Les først:** «Serverne» i `docs/systemer/publisering.md`, `tools/server/setup.sh`, og «Nede» i `docs/systemer/tilbakemelding-og-admin.md`.

**Det økta ikke kan:** kjøre `setup.sh` på serveren (ikke root). Det går til Jonas i `docs/spill-dette/138.md`.
